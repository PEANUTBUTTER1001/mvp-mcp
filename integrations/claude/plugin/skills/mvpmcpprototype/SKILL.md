## 방안 찾기 (mvpmcp 문서 연결)

아래 `# HTML 프로토타입` 절차의 "방안"은 mvp-mcp가 만든 문서다.

- 인자로 문서 경로(폴더 또는 파일)를 주면 그것을 방안으로 쓴다. 반영 전 후보(generate_only·manual_apply)는 후보 폴더 경로를 인자로 받는다.
- 인자가 없으면 작업공간 `.mvpmcp/*/docs/` 중 가장 최근에 수정된 폴더의 `*.md` 전체를 방안으로 쓰고, 어떤 폴더를 썼는지 완료 보고에 적는다.
- 둘 다 없으면 "먼저 `/mvpmcp:mvpmcp`로 문서를 만드세요"라고 보고하고 멈춘다.
- 이전 Run에 남은 `MVPDESIGN.md`·`design-tokens.json`·`prototype/`은 방안으로 쓰지 않는다. 화면·기능 근거는 REQUIREMENTS·ARCHITECTURE 등 문서에서 얻는다.
- mvp-mcp 도구를 호출하지 않고 `.mvpmcp/` 아래에 쓰지 않는다. 저장 위치는 아래 작업 절차 3을 따른다.

# HTML 프로토타입

주어진 방안을 사용자가 로컬에서 바로 열어 볼 수 있는 독립형 HTML 프로토타입으로 만든다.

## 작업 절차

1. 방안에서 제품 목표, 대상 사용자, 주요 화면, 핵심 사용자 흐름, 콘텐츠, 시각 방향을 추출한다.
2. 빠진 표현 세부 사항은 위험이 낮은 범위에서만 가정한다. 누락된 결정이 프로토타입을 크게 바꿀 때만 짧게 질문한다.
3. 요청한 위치에 독립 실행형 `.html` 파일 하나를 만든다. 위치가 없으면 작업공간의 `outputs/` 디렉터리에 결과물을 저장한다.
4. CSS와 JavaScript는 모두 파일 안에 포함한다. 핵심 동작에 빌드 과정, 프레임워크, 서버, API 키 또는 외부 에셋이 필요하지 않게 한다.
5. 현실적인 예시 데이터를 사용해 방안의 중요한 상태와 상호작용을 구현한다. 버튼과 컨트롤은 눈에 보이는 반응이 있어야 하며, 명시된 기능에 작동하지 않는 컨트롤을 남기지 않는다.
6. 시맨틱 HTML, 반응형 CSS, 키보드로 조작 가능한 컨트롤, 명확한 포커스 상태, 충분한 색 대비를 적용한다.
7. 가능하면 브라우저 또는 로컬 미리보기로 결과를 점검한다. 전달 전에 명백한 레이아웃, 넘침, 대비, 상호작용 문제를 수정한다.

## 디자인 지침

- 의도적인 서체 크기 체계, 간격 체계, 절제된 색상 팔레트로 일관된 시각적 위계를 만든다.
- 일반적인 와이어프레임보다 설득력 있는 제품 화면을 우선한다. 필요할 때 그럴듯한 라벨, 빈 상태, 유효성 검사, 피드백, 예외 상황을 넣는다.
- 명시된 브랜드 가이드, 참고 이미지 또는 스타일 지시를 따른다. 없으면 제품에 어울리는 깔끔하고 현대적인 방향을 선택한다.
- CSS, 마크업, 데이터, 동작 영역을 구분해 코드를 읽기 쉽게 유지한다.
- 결과물은 프로토타입으로 다룬다. 외부 데이터는 모의 처리하고, 사용에 영향을 줄 때만 한계를 명확히 알린다.

## 완료 보고

생성한 파일을 클릭 가능한 작업공간 링크로 보고하고, 구현한 화면과 상호작용을 한두 문장으로 요약한다.
